# Acceptance reporting

Read this reference before closing an Audit, Setup or repair, or Acceptance run. Include only applicable rows; preserve the result vocabulary from `SKILL.md`.

## Report shape

Lead with two independent verdicts and the highest evidence level reached:

- **Execution result:** whether the selected Audit, Setup or repair, or Acceptance process completed as scoped.
- **Target readiness:** whether the requested Flutter development/runtime workflow is ready based on current evidence.

Use `PASS`, `WARN`, `SKIP`, or `FAIL` for each verdict. A complete Audit can be `PASS` while target readiness is `FAIL` or `WARN`; keep both facts visible.

For each `WARN`, `SKIP`, or `FAIL`, state the first boundary, impact on the requested Flutter workflow, and exact next action. Do not add rows merely to fill the template.

## Change accounting

List configuration and repository files changed, including the reason for each. Report generated or ignored artifacts separately. Confirm whether the final repository worktree contains only task-owned changes; if not, distinguish pre-existing changes.

When credentials, tokens, fixed identifiers, temporary mirrors, or debug bypasses were used during validation, state whether they were removed. Production handoff requires the normal credential and environment-selection path to be restored.

## Claim checks

Before sending the report, verify:

- every `PASS` is backed by output or runtime observation from this run;
- every required gate has a row;
- simulator/emulator evidence is not labeled physical-device evidence;
- module evidence is not labeled native-host evidence;
- build evidence is not labeled live-service evidence;
- dated documentation or historical results are identified as context rather than current validation;
- unavailable real-device checks are `SKIP`, never `PASS`.
